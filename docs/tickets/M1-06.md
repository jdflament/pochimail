# M1-06 · Action command pattern: idempotency, inverse, Apply/Undo use cases

**Draft ID:** M1-06 · **Labels:** `type:feature` `area:core` `p0` · **Size:** L · **Blocked by:** M1-03, M1-05 · **Packages:** packages/core

**Read first:** docs/brief.md §5.3 (idempotent actions), §5.6; docs/adr/0003-hexagonal-core-events-outbox.md

**Context**
Actions change real mailboxes. They must be replay-safe and reversible, including after a restart.

**Scope**
- Action command with idempotency key and computed inverse.
- `ApplyAction` use case: authorize → execute through MailProvider → record in ActionLog → emit event, all via UnitOfWork.
- `UndoAction` use case (per action and per batch) that reads the inverse from the repository, so undo works after a process restart.
- Partial-failure handling: batch continues, failures are recorded and surfaced.

**Acceptance criteria**
- [ ] Applying the same action twice (same idempotency key) mutates the provider once (named test).
- [ ] Undo after constructing a fresh use case instance over the same repository restores prior state.
- [ ] A provider failure mid-batch leaves a correct ActionLog (applied vs failed) and undo only reverses applied ones.
- [ ] An unauthorized action is not sent to the provider and is logged as refused.
- [ ] Contract: works against any `MailProvider` implementing the capability set.
- [ ] Test bar: behaviour tests through public entry points only (no tests of private helpers); each test guards a named failure (its name states the bug it prevents); contract suites are exported so M2 adapters (SQLite, real providers) reuse them unchanged.

**Out of scope**: Offline queue (M5), UI undo toast (M5).
