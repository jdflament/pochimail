# M2-07 · rate limiting, backoff and Retry-After → RateLimited

**Draft ID:** M2-07 · **Labels:** `type:feature` `area:mail` `p0` · **Size:** M · **Blocked by:** M2-06 · **Packages:** packages/mail

**Read first:** docs/brief.md §5.3 › Provider efficiency; docs/adr/0004-incremental-sync-and-imap.md (Rate limits, Gmail quota units, Graph limits); docs/security/oauth-verification.md (quota notes)

**Context**
One shared mechanism so Gmail, Graph and IMAP adapters all turn throttling into the `RateLimited{resumeAt}` error core already handles.

**Scope**
- Per-account token bucket (Gmail counted in quota units: get 20, list 5, history.list 2, batchModify 50; Graph per-request and `$batch` of 20; IMAP connection-count limit).
- Exponential backoff with jitter; honour `Retry-After` / provider throttle headers; map to core `RateLimited` with `retryAfterMs`.
- Deterministic with an injected `Clock`/random source.

**Acceptance criteria**
- [ ] Burst beyond the bucket waits instead of calling out (named test with fake clock).
- [ ] `Retry-After: 30` yields `RateLimited` with the right `resumeAt`; backoff delays grow and are jittered within bounds.
- [ ] Buckets are per account: one account throttled does not slow another (named test).
- [ ] Core's `RunIncrementalSync` pauses into the right account state with this error (integration test against the fake provider).
- [ ] Test bar: behaviour tests through public entry points only (no tests of private helpers); each test guards a named failure (its name states the bug it prevents); contract suites are exported so M2 adapters (SQLite, real providers) reuse them unchanged.

**Out of scope**: Provider-specific request code (M2-09..13).
